# 実データ調査結果（ground truth / 2026-07-30 実測）

`data/raw/` の実データを **ヘッダ + 先頭数行のみ** 読んで確認した事実。
全データ読み込みは禁止（1年分では数十GBになる）。以降の設計・実装はこの事実を前提にする。

## 0. サマリ（設計に直結する重大事実）

1. **trend は VIN を持たない**。キーは `DATETIME`（1分粒度の時系列）。→ VIN 結合ではなく**時刻結合**が必要。
2. **trend と traceability/defect の期間が重複していない**（trend=07/29-07/30、他=07/24-07/25）。→ このサンプルでは VIN×trend 結合の結果は必ず空。実装は正しく書けるが、サンプルでの検証は不能。
3. **traceability は「1ソース=1設備の横長テーブル」**。設備名を列に注入して縦持ちにする従来設計（`docs/real_data_ingest_design.md`）は実データの形と合わない。ソース毎に列名プレフィクスを付けて VIN で横結合するのが自然。
4. **ファイル毎にスキーマが全く異なる**（列数 10〜621）。共通スキーマ前提は成立しない。
5. **VIN は 18 文字固定・右空白パディング**。`a` サフィックス（再塗装/2トーン2回目）・`DUMMY`/`EMPTY`（ダミー台車）が下流工程のみに存在。※ 追記で補正（§5参照。サフィックス付き VIN の空白は内部にあり `strip()` では不十分／サフィックスは `a`/`b`/`c`／ダミー実値は `DUMMY-YOSHIKI` と `EMPTY`）。
6. エンコーディングは全ファイル **UTF-8 (BOM付き)** → `encoding="utf-8-sig"`。
7. 列名は半角カナ・空白・`#`・`(大)` 等を含む（例: `ｿﾞｰﾝ#1 循環 還気 温度 測定値`）。

## 3. VIN（結合キー）の実態

| ファイル | 行数 | uniq(raw) | uniq(strip) | サフィックス分布 |
|---|---:|---:|---:|---|
| シーラー炉 | 902 | 902 | 902 | なし |
| ブース | 1,216 | 1,216 | 1,216 | なし958 / 空白234 / `a`22 / `DUMMY`2 |
| ホイ黒ロボット | 1,896 | 948 | 948 | なし1398 / 空白454 / `a`44 |
| 上塗ロボット | 36,478 | 1,218 | 1,218 | なし28738 / 空白7020 / `a`660 / `DUMMY`60 |
| 下塗ロボット | 16,942 | 901 | 901 | なし |
| 中上炉 | 1,216 | 1,216 | 1,216 | ブースと同分布 |
| 前処理 / 電着 / 電着炉 / 各工程滞在時間 / 浮遊ゴミ | 886〜891 | 同数 | 同数 | なし（浮遊ゴミに `EMPTY` 1件） |
| 上塗ブツ検 | 8,024 | 933 | 933 | なし7783 / 空白228 / `a`13 |
| 電着ブツ検 | 21,726 | 893 | 893 | なし |

要点:
- **右空白パディングで18文字固定** → `str.strip()` 必須（`"MR92S-617408      "`）。※ 追記で補正: サフィックス付き VIN は空白が末尾ではなく**内部**にあるため `strip()` だけでは不十分（§5参照）。
- `strip()` しても unique 数は変わらない = 空白違いだけの重複 VIN は無い。
- VIN 形式は2系統: 型式ベース `MR92S-617408` / `HE93S-122040`、およびフル VIN `JS3JB74V8V5106401`。
- **`a` サフィックス**（例 `HE93S-122023     a`）は下流工程（ブース・中上炉・上塗ロボット・ホイ黒・上塗ブツ検）にのみ出現。上流（前処理・電着・電着炉・下塗ロボット・シーラー炉）には無い。2トーン車の2回目通過/再塗装と推定。**別 VIN として扱うか同一車体に丸めるかは業務判断が必要（未確定）**。※ 追記で補正: サフィックスは `a` だけでなく `b`/`c` も実在する（§5参照）。
- `DUMMY` / `EMPTY` はダミー台車 → 分析対象外として除外すべき。※ 追記で補正: ダミーの実値は `DUMMY-YOSHIKI`（+サフィックス `d`/`e`）と `EMPTY`。`DUMMY` 完全一致では拾えない（§5参照）。
- VIN 数の差（上流886 vs 下流1216）は上記 `a` 行とダミー行に由来。

## 4. 1年分へのスケール見積り

1日 = 41MB。稼働日 250日/年 とすると:
- 生CSV 合計: **約 10GB/年**（ブース trend 単独で 2.6GB/年、上塗ロボット traceability 1.4GB/年）
- 行数/年: 上塗ロボット約 910万行、電着ブツ検 約 540万行、trend 各約 29万行
- 列数は変わらない（最大 621列）

→ 全 CSV を pandas に一括ロードするのは不可。**ファイル単位のストリーミング読み込み → Parquet 化（日付パーティション）→ 必要列のみ読む**構成が必須。

## 5. 実測補正（2026-07-30 追記）

VIN 列のみを対象に再実測した結果、上記 §0/§3 の記述だけでは不足があったため、以下を正とする
（`docs/real_data_ingest_design.md` §1.1 と同一内容）。

1. **サフィックス付き VIN の空白は文字列の内部にある。**
   実値: `"HE93S-122023     a"`（18文字, 内部に半角空白5個）、`"JS3JB74V8V5106396a"`（空白なし）。
   → `str.strip()` では `a` の前の空白が残る。**`str.replace(r"\s+", "", regex=True)` を使う**。
   全空白除去後の unique 数は `strip()` 後と全ファイルで一致 → 空白除去による衝突は無い（安全）。
2. **サフィックスは `a` だけではない。`a` / `b` / `c` が実在する**（1日分の実測: ソース毎に a≈252, b=1, c=1）。
   さらにダミーには `d` / `e` が付く。→ 単一文字 `a` のハードコードは誤り。`[a-z]$` で扱う。
3. **ダミーの実値は `DUMMY-YOSHIKI`（+ サフィックス `d`/`e`）と `EMPTY`**。`DUMMY` 完全一致では拾えない
   → 部分一致で判定する。
4. **VIN は2形式が混在する**: 型式ベース `[A-Z0-9]{5}-\d{6}`（例 `MR92S-617408`）と 17桁フル VIN
   `[A-Z0-9]{17}`（例 `JS3JB74V8V5106401`）。1ファイル内に両方が出現し、件数は排他的
   （前処理: 784 + 102 = 886）。→ 別車体を指すと推定するが**未確定**。

## 6. 実測補正（2026-08-28 追記。データが1か月分の実データ相当に差し替え）

`data/raw/` が旧サンプル（1日分・trendとtraceabilityが非重複期間）から、より実データに近い
1か月分（2026年1月）のデータに差し替えられた。これに伴い、§0 の前提の一部が**もはや成立しない**。

1. **§0-2「trendとtraceability/defectの期間が重複していない」は今回のデータでは成立しない。**
   新データは両者とも 2026-01 の同一期間に収まっており、実際に `assemble` を実行すると
   trend結合のマッチ率が 78〜85%（VIN 21,020件）まで達する（旧サンプルの「必ず0%」という
   前提はサンプル固有の制約であり、実装の欠陥ではなかったことが実データで裏付けられた）。
   `docs/real_data_ingest_design.md` の D7・§12.6 参照。
2. **日時形式が全ファイルで完全一致しない。ソースによって秒あり/秒なしが混在する。**
   `real_data_ingest_design.md` §1 の「日時形式は全ファイル `%Y/%m/%d %H:%M:%S` で完全一致」は
   旧サンプル固有の事実であり、新データでは不成立。実測（2026-08-28）:
   - **秒あり（`%Y/%m/%d %H:%M:%S`。従来通り）**: traceability の シーラー炉・ホイ黒ロボット・
     中上炉・前処理・各工程滞在時間・浮遊ゴミ・電着・電着炉、defect の 上塗ブツ検・電着ブツ検。
   - **秒なし（`%Y/%m/%d %H:%M`。ゼロ埋めも無し。例 `2026/1/2 16:35`）**: traceability の
     **ブース・上塗ロボット・下塗ロボット**、**trend 全7ソース**。
   - センサー/PLC 系（ブース・ロボット・trend）が分単位ロギング、VIN 通過・検査イベント系が
     秒単位、という実データらしい傾向と考えられる（未確定）。
   - 対応: `real_ingest.convert.datetime_format_fallbacks`（主フォーマット失敗分だけ順に再トライ。
     コード既定値に `["%Y/%m/%d %H:%M"]` を含む）を追加した。`src/defect_analysis/raw_convert.py`
     の `_parse_datetime_with_warning()`。
   - 実装上の注意（回帰済みバグ）: 主フォーマットが列内で全滅すると pandas は
     `datetime64[s]` に解像度を推定し、フォールバックが返す `datetime64[us]` と食い違う。
     列間で解像度が揃わないと後段の `merge_asof`（trend結合）が
     `MergeError: incompatible merge keys` で例外を投げるため、パース結果は必ず
     `.dt.as_unit("us")` で解像度を揃える。
